# BASEへの導入：制約と実装方針

> 対象：BASE＋TIMELESSテーマ＋商品説明カスタムApp＋THE CKB連携App＋広告効果測定App（Meta Pixel）
> 商品ID：165450879（現在は非公開で、全SKUの在庫は0）
> この試作では BASE の設定に一切触れていません。以下は公開を検討するための整理です。
> BASE のApp仕様やテーマの対応範囲は変わることがあります。【要確認】の項目は、BASEの管理画面・ヘルプ・各Appの説明で最新情報を確かめてから判断してください。

---

## 1. BASE標準テーマ（TIMELESS）＋商品説明カスタムAppで再現できる部分

| LPの要素 | 再現性 | 方法 |
|---|---|---|
| 商品画像ギャラリー・商品名・価格・カラー（SKU）選択・カートボタン | ◎ | BASE標準の商品ページ機能。カート・SKU・在庫はこれを使うことになる |
| 圧縮前後の比較画像、収納構造の写真、使用シーンの写真 | ○ | 商品説明カスタムAppの画像ブロックで配置する。全幅で見せられるかはテーマ次第【要確認】 |
| 見出し＋本文のセクション（メリット、使い方、配送・返品） | ○ | 商品説明カスタムAppの見出し・テキスト・画像ブロックを組み合わせる |
| 実演動画 | △ | YouTube埋め込みが使えるかはAppによる【要確認】。使えない場合はGIFや静止画で代用する |
| 仕様表 | △ | 表ブロックがなければ、テキストか画像の表にする（画像の表は検索・読み上げに不利） |
| FAQ | △ | アコーディオンが使えなければ、Q&Aをテキストで並べる |

## 2. BASEでは再現が難しい部分

| 要素 | 理由・代わりの案 |
|---|---|
| **PCで購入エリアの下を全幅にする構成** | 標準テーマでは、商品説明が購入情報と同じカラムやテーマの決まった幅に収まることが多く、今のBASEページのような細い右カラムになりやすい。全幅にするには HTML編集App で独自テーマにする必要がある【要確認】 |
| スマホの固定購入バー（表示・非表示の制御を含む） | テーマ側の機能。独自のJSを入れるには HTML編集App が必要 |
| `site-config.js` で実測値を一括で差し替える仕組み | 商品説明は管理画面での手入力になるので、実測値の更新は手作業で複数箇所を直す |
| 実測中バッジ・プレースホルダーのデザイン | 文字や画像としてなら表現できる |
| 構造化データ・OGPを細かく制御すること | BASEが自動で出力する。個別に制御するのは難しい |
| ブランドトップページ（独自構成） | BASEのトップは商品一覧が中心。独自の構成にするには HTML編集App か外部サイトが必要 |

## 3. 実際に公開する場合の実装方法（3案）

### 案A：BASE内で完結（TIMELESS＋商品説明カスタムApp）……まずはこれを推奨
- LPの各セクションを商品説明カスタムAppで再構成する。画像は、文字を焼き込まない写真を中心にする。
- **メリット**：カート・SKU・在庫・CKB連携・Meta Pixel（広告効果測定App）が今の設定のまま動く。リスクがいちばん低い。
- **デメリット**：PCで全幅に展開する構成や固定購入バーは再現できない。

### 案B：BASEの HTML編集App で独自テーマにする
- このプロトタイプのHTML/CSSを、BASEのテーマテンプレート（BASE独自のタグで商品名・価格・カートボタンなどを出力する仕組み）に移植する。
- **メリット**：BASEのカートやSKUを使ったまま、デザインをほぼ再現できる。
- **デメリット／注意点**
  - TIMELESS のような公式テーマを直接編集できるとは限らず、ゼロから組み直しになる可能性がある【要確認】
  - 他のApp（商品説明カスタムApp など）との両立を確認する必要がある【要確認】
  - 広告効果測定App のPixelタグが独自テーマでも自動で入るかを、公開前に確認する【要確認】
  - テーマを切り替えると、ショップ全体の見た目が変わる。テスト用のショップで検証するのが望ましい

### 案C：外部LP（独自ドメイン）＋BASEの商品ページに遷移
- このプロトタイプを静的ホスティングで公開し、購入ボタンは BASE の商品ページ `https://＜ショップ＞.base.shop/items/165450879` へのリンクにする（`site-config.js` の `purchase.url` に設定するだけ）。
- **メリット**：デザインの自由度が最も高い。Meta広告の遷移先として最適化しやすい。
- **デメリット**：LP → BASE と1ステップ増える。外部サイト側に Pixel を別途設置する必要がある（下記5）。
- 外部サイトからBASEのカートに直接商品を入れる公式の手段は、ないものとして設計する【要確認】。

> 推奨の進め方：**まず案Aで販売を始め**、広告の遷移率や購入率を見てから、案C（または案B）を検証する。

## 4. カート・SKU・在庫・CKB連携を維持する方法
1. **既存の商品（ID 165450879）を使い続ける**。複製や新規作成をすると、CKB側の商品の紐づけ（SKUの対応）が切れるおそれがある。
2. カラー・モデルといったSKUの構成は BASE の「種類（バリエーション）」で管理する。LP側で独自の選択肢を作っても、BASEのSKUとはつながらない。将来カラーを追加するときは、BASE側でSKUを追加し、CKBとの対応も更新する。
3. **在庫数は BASE（とCKB連携）だけで管理する**。LPに在庫数や「残りわずか」を表示する場合は、BASEのデータと連動しないので、表示しないか手動更新を前提にする。
4. 決済は必ず BASE のチェックアウトを通す（このプロトタイプには決済機能を実装していません）。注文がBASEに入ることで、CKBの出荷連携が動く。
5. 公開前のチェック：テスト注文の扱い（CKBに出荷指示が流れないか）を CKB 側と事前に確認する。

## 5. Meta Pixel の計測を維持するための注意点
- **二重設置をしない**：広告効果測定App で設置済みのため、HTML編集App やテーマに同じ Pixel のコードを手で追加しない（イベントが二重に計測される）。
- **BASE内で計測されるイベント**（PageView／ViewContent／AddToCart／InitiateCheckout／Purchase など）は、App の仕様に依存する。公開前に Meta のイベントマネージャ「テストイベント」と Meta Pixel Helper で、どのイベントが発火しているか実際に確認する【要確認】。
- **案Cで外部LPを使う場合**
  - LPに **同じPixel ID** のベースコードを設置し、PageView と ViewContent（`content_ids` は 165450879 を推奨）だけを送る。**Purchase はLPから送らない**（BASE側に任せる）。
  - 購入ボタンのクリックをカスタムイベント（例：`ClickToBASE`）で計測すると、LP → BASE の遷移率が分かる。
  - 独自ドメインは Meta ビジネスマネージャで **ドメイン認証** を行い、ウェブイベントの設定（優先度など）も確認する。
  - ドメインが分かれると Cookie（_fbp）が共有されないので、広告URLの `fbclid` を活かせるよう、リダイレクトでパラメータが落ちないようにする。UTM も付けて、BASEのアクセス解析と照合する。
- **広告の遷移先を変えるとき**：URLを変えると、配信の学習がリセットされたり計測が途切れたりする可能性がある。新しいLPはA/Bテストか新しい広告セットで検証し、切り替えの前後で CV 計測が続いているか確認する。
- **プライバシー**：外部LPで Pixel を使う場合は、プライバシーポリシーの記載（電気通信事業法の外部送信規律への対応を含む）を整える。

## 6. このプロトタイプから移植するときのチェックリスト
- [ ] 実物の写真・動画を撮影し、`site-config.js` の `media` に設定（AI生成画像は使わない）
- [ ] 実測データを `product.measured` に入力（測定条件も記載）
- [ ] 配送・返品・決済の文言をBASEのショップ設定と一致させる
- [ ] 特定商取引法の表記・プライバシーポリシーへのリンクを設定
- [ ] `robots: noindex`、デモバナー、DEMO表示を外す（案Cの場合）
- [ ] `canonical`・`og:image` の URL を本番のものに変更
- [ ] 販売開始時に、構造化データの `offers`（価格・在庫状況）を追加
